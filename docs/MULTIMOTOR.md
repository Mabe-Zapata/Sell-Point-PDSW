# Multimotor SQL — Sell-Point

## Overview

The application supports running against **PostgreSQL** or **Oracle** with a single codebase. The multimotor layer handles engine-specific differences in types, DDL, and features automatically.

---

## Quick Start

### 1. Choose your engine

Edit `.env`:

```env
# For PostgreSQL
DB_TYPE=postgres

# For Oracle
DB_TYPE=oracle
```

### 2. Start the containers

```bash
docker compose up -d
```

For **Oracle**, the `APP_USER` schema is created automatically on first start via `docker/oracle/startdb/001_create_app_user.sh`.

### 3. Run migrations

```bash
npm run typeorm:migration:run
```

To revert the last migration:

```bash
npm run typeorm:migration:revert
```

## Engine Comparison

| Feature | PostgreSQL | Oracle |
|---|---|---|
| **Boolean type** | `boolean` | `number(1)` |
| **Long text** | `text` | `varchar2(4000)` |
| **UUID primary key** | `uuid` | `varchar(36)` |
| **INCREMENTAL PK** | `GENERATED BY DEFAULT AS IDENTITY` | `GENERATED BY DEFAULT AS IDENTITY` |
| **Materialized views** | `CREATE MATERIALIZED VIEW IF NOT EXISTS` | `CREATE MATERIALIZED VIEW` |
| **Partitioning** | Declarative (parent + child tables) | Native (in-table partitions) |
| **Unique index on partitioned table** | Must include partition key | Must include partition key |
| **Text in CHECK constraints** | `text` type allowed | Must use `varchar2` |

## Architecture

### Entities — `db-column.helper.ts`

All entities use two helper functions to bridge the type gap:

```typescript
// Booleans: postgres=boolean, oracle=number(1)
dbBooleanColumn(defaultValue?: boolean)
  // → { type: 'boolean', default: true }  // postgres
  // → { type: 'number',  default: 1 }    // oracle

// Long text: postgres=text, oracle=varchar2(4000)
dbLongTextColumn(nullable?: boolean)
  // → { type: 'text', nullable: true }     // postgres
  // → { type: 'varchar2', length: 4000, nullable: true }  // oracle
```

### Migration — `1800000000001-SchemaBaseline.ts`

Uses TypeORM's `Table` + `TableColumn` abstraction with inline engine shims:

```typescript
const boolType    = dbType === 'oracle' ? 'number' : 'boolean';
const boolDefault = dbType === 'oracle' ? 1        : true;
const longTextType = dbType === 'oracle' ? 'varchar2' : 'text';
```

### Views — `1800000000002-CreateMaterializedViews.ts`

Raw SQL for both engines. Key differences:
- **Postgres**: double-quoted identifiers, `COALESCE`, `date_trunc`, `IF NOT EXISTS`
- **Oracle**: bare uppercase identifiers, `NVL`, `TRUNC`, no `IF NOT EXISTS`
- Oracle SALES primary key is quoted `"id"` — this is a known TypeORM/Oracle quirk

### Partitioning — `1800000000003-AddPartitioningScaffold.ts`

Drops and recreates `SALES` as a **HASH partitioned table** with 4 partitions.

- **Postgres**: declarative `PARTITION BY HASH` with child tables `SALES_P0`–`SALES_P3`
- **Oracle**: native `PARTITION BY HASH ... PARTITIONS 4`
- **Other engines**: no-op

> **Note**: Because `SALES` is partitioned by `id`, the `SAL_NUM` index cannot be unique (Postgres requirement). It remains a regular index.

## Known Quirks

### Oracle — Quoted Identifiers

TypeORM creates the `SALES.id` column as a **quoted, case-sensitive identifier** (`"id"`). All SQL referencing it must use `"id"` when running against Oracle.

The materialized views migration handles this with a shim:

```typescript
const salesIdRef = dbType === 'oracle' ? '"id"' : 'id';
// → SALES."id" for Oracle, SALES.id for Postgres
```

### Oracle — APP_USER Only on First Start

`gvenzl/oracle-free` creates `APP_USER` only during the **first initialization** of the container volume. Changing `.env` after the first start does not recreate the user.

The startup script at `docker/oracle/startdb/001_create_app_user.sh` runs on **every boot** and uses `CREATE OR REPLACE` semantics to be idempotent.

To force a fresh Oracle init:

```bash
docker compose down -v
docker compose up -d
```

### Postgres — Unique Index + Partition Key

A unique index on a partitioned table **must include all columns of the partition key**. Because `SALES` is partitioned by `id`, the `SAL_NUM` index cannot be unique. It is a regular index instead.

### Oracle — VARCHAR2 vs TEXT

Oracle does not have a `text` type. Long文本 fields use `varchar2(4000)`. The `dbLongTextColumn()` helper handles this automatically.

## Troubleshooting

### ORA-01017 — Invalid credentials (Oracle)

The app user does not exist in the database. Run:

```bash
docker compose restart oracle
```

Or force a clean init:

```bash
docker compose down -v
docker compose up -d
```

### ORA-00904 — Invalid identifier (Oracle)

Likely a quoted identifier issue with `SALES.id`. The migration uses `"id"` (quoted lowercase) for Oracle.

### NJS-518 — Service not registered (Oracle)

TypeORM is missing the `connectString`. This is configured in `typeorm.config.ts`:

```typescript
extra: {
  connectString: `${host}:${port}/${database}`,
}
```

### type "number" does not exist (Postgres)

An entity or migration used `type: 'number'` (Oracle-only) with Postgres. All entities must use `dbBooleanColumn()` for booleans and the baseline migration uses inline engine shims.

### syntax error at or near "PARTITION" (Postgres)

`ALTER TABLE ... PARTITION BY` is not valid DDL in Postgres. The table must be created as partitioned from the start, which is what migration 3 does.
